# Auto-deploy to Coolify

Every push to `main` runs **CI**. When CI passes, **Deploy** (`.github/workflows/deploy.yml`) builds the four images, pushes them to GHCR as `sha-<commit>` with an SBOM and signed provenance, sets `TAG` on the Coolify resource and starts a Coolify deployment, then waits for it to finish. Release tags (`vX.Y.Z`) and a manual run from `main` do the same. Coolify itself never builds: it pulls the images CI built.

```
push to main ─▶ CI (tests, lint, scans, image build) ─▶ Deploy: build + push images ─▶ Coolify: TAG=sha-…, deploy
```

The stack Coolify runs is `deploy/coolify/docker-compose.yml`: API, image worker, storefront, admin, MongoDB (single-node replica set) and Redis. Coolify's Traefik serves HTTPS, so there is no Caddy. Passwords, the Mongo keyfile and internal tokens are Coolify-generated variables.

The deploy workflow stays switched off until step 4 sets `COOLIFY_APP_UUID`, so pushes before then only run CI.

## 1. DNS

Point the storefront, `admin.` and `api.` domains (A/AAAA) at the Coolify server that will run the app (for example sr2, `38.49.214.105`). The media CDN domain stays on Cloudflare R2.

## 2. Create the resource in Coolify

1. **Projects → AT Creations → production → + New → Public Repository**.
2. Repository URL `https://github.com/at-creations/atcreations`, branch `main`, server **sr2**.
3. **Build Pack: Docker Compose**, **Docker Compose Location: `/deploy/coolify/docker-compose.yml`**, then **Continue**.
4. **Advanced → turn off "Auto Deploy"**. GitHub Actions deploys after CI passes, and Coolify must not also deploy every push (it would deploy before the images exist).
5. **Domains** (in the service list on the resource's page; the port is where the container listens):

   | Service | Domain |
   |---|---|
   | storefront | `https://atcreations.ca:3000` |
   | admin | `https://admin.atcreations.ca:3000` |
   | api | `https://api.atcreations.ca:8080` |
   | imgworker, mongo, redis | leave empty (internal only) |

6. **Environment Variables**: Coolify lists every `${VAR}` from the compose file. Fill in:

   | Variable | Value |
   |---|---|
   | `TAG` | `sha-pending` (the Deploy workflow replaces it before every deployment) |
   | `STOREFRONT_DOMAIN`, `ADMIN_DOMAIN`, `API_DOMAIN` | bare host names: `atcreations.ca`, `admin.atcreations.ca`, `api.atcreations.ca` |
   | `CLERK_SECRET_KEY`, `PUBLIC_CLERK_PUBLISHABLE_KEY` | the **production** Clerk instance (`sk_live_…`, `pk_live_…`) |
   | `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Cloudflare R2 bucket and an API token scoped to it |
   | `CDN_BASE_URL` | the bucket's public domain, for example `https://cdn.atcreations.ca` |
   | `SENDGRID_API_KEY`, `MAIL_FROM` | SendGrid key and the verified sender (`orders@atcreations.ca`) |

   Optional, with defaults: `S3_KEY_PREFIX` (`atcreations`: the folder every object goes in, see below), `S3_REGION` (`auto`), `MAIL_PROVIDER`, `MAIL_FROM_NAME`, `STORE_NAME`, `FEATURE_PUBLIC_CHECKOUT` (`false`), `ANALYTICS_TIMEZONE`, `LOG_LEVEL`, `TRUSTED_PROXIES` (see step 6).

   The `SERVICE_PASSWORD_*` and `SERVICE_BASE64_64_MONGOKEYFILE` values are generated by Coolify on the first deploy. **Copy them into your password manager**: the database can't be opened without them.

7. Copy the resource's UUID from its URL (`…/application/<uuid>`). Don't press Deploy yet: there are no images until the workflow builds them.

## 3. Coolify API token

**Keys & Tokens → API Tokens → Create**, named `github-deploy`, with the **write** and **deploy** permissions. It needs `write` to set `TAG` and `deploy` to start the deployment.

## 4. GitHub settings

In `github.com/at-creations/atcreations` → **Settings**:

1. **Environments → New environment `production`**:
   - **Deployment branches and tags:** selected branches and tags, `main` and `v*.*.*`.
   - **Environment secret** `COOLIFY_TOKEN` = the token from step 3.
   - Optional: **Required reviewers** if you want to approve each deploy.
2. **Secrets and variables → Actions → Variables** (repository variables). The frontends compile these into their Content Security Policy at build time:

   | Variable | Example |
   |---|---|
   | `PUBLIC_API_URL` | `https://api.atcreations.ca` |
   | `PUBLIC_ASSET_BASE_URL` | `https://cdn.atcreations.ca/atcreations/site` (CDN + `S3_KEY_PREFIX` + `/site`) |
   | `CSP_IMG_ORIGINS` | `https://cdn.atcreations.ca` |
   | `PUBLIC_CLERK_PUBLISHABLE_KEY` | `pk_live_…` |
   | `CSP_CLERK_ORIGINS` | your Clerk Frontend API origin, for example `https://clerk.atcreations.ca` |
   | `COOLIFY_URL` | `https://coolify.baoopn.com` |
   | `PRODUCTION_URL` | `https://atcreations.ca` (shown on the deployment) |
   | `COOLIFY_APP_UUID` | the UUID from step 2.7. **Set this last**: it switches the Deploy workflow on |

## Sharing the bucket with the old site

The new app can use the old site's R2 bucket. Every object it writes (product and category images, upload staging, site photos) goes under `S3_KEY_PREFIX` (default `atcreations/`), and it only ever reads, lists or deletes inside that folder, so the two never touch each other's files. Image URLs become `CDN_BASE_URL/atcreations/products/...`.

- Before the first deploy, check in the R2 dashboard that the bucket has no `atcreations/` folder yet. If it does, pick another `S3_KEY_PREFIX`.
- Give the new app its own R2 API token for that bucket (Object Read & Write). Don't reuse the old site's token, so either can be revoked on its own.
- Upload the storefront's site photos (logo, shop photos: the files in `docker/dev/site-assets/`) to `atcreations/site/` in the bucket.
- Upload staging (`atcreations/uploads/`) holds originals for a few minutes until they're processed. An R2 lifecycle rule on that prefix (delete after 1 day) is a good safety net. Don't add one for the whole bucket.

## 5. First deploy

1. **Actions → Deploy → Run workflow** on `main`.
2. When the images are pushed, open **github.com/orgs/at-creations/packages** and check that the four `atcreations-*` packages are **Public**. Packages pushed from a public repository usually are; if one is private, open it → **Package settings → Change visibility → Public**. Otherwise Coolify can't pull it, unless you instead run `docker login ghcr.io` on the server with a token that has `read:packages`.
3. The workflow sets `TAG`, starts the Coolify deployment and fails the run if Coolify reports a failure. On first boot MongoDB initialises its replica set and creates the `atcreations_app` user before the API starts.
4. In Clerk, set your user's `publicMetadata` to `{"role":"admin"}`, then sign in to the admin dashboard.

From then on, every push to `main` that passes CI is deployed automatically.

## 6. After the first deploy

- **Narrow `TRUSTED_PROXIES`.** It defaults to all private ranges. On the server, `docker network inspect <resource-uuid> --format '{{(index .IPAM.Config 0).Subnet}}'` prints the subnet that Coolify's proxy and the storefront share. Set `TRUSTED_PROXIES` to it and redeploy.
- **Backups.** MongoDB lives in the `mongo_data` volume. Coolify doesn't back up a database defined inside a Compose file, so schedule `mongodump` (Coolify **Scheduled Tasks** on the `mongo` service, or `deploy/scripts/backup.sh` adapted to the container name) and copy the archives off the server.
- **Data.** A new deployment starts with an empty database. Restore a dump (`mongorestore`) or run `apps/api/cmd/migrate` against it to bring the catalogue across.

## Rolling back

Every image stays in GHCR. To roll back, open an earlier successful **Deploy** run in Actions and choose **Re-run all jobs**. It redeploys that run's commit. A manual alternative is to set `TAG` to an older `sha-<commit>` in Coolify and press **Deploy**.

## Verifying an image

```bash
gh attestation verify oci://ghcr.io/at-creations/atcreations-api:sha-<commit> --owner at-creations
```
